# T04 — CAP Research


## 1. Định nghĩa CAP Theorem

Định lý CAP (Brewer 2000, chứng minh bởi Gilbert & Lynch 2002) phát biểu: một hệ phân tán
không thể đồng thời đảm bảo cả ba tính chất sau khi xảy ra network partition:

- **Consistency (C)** — Linearizability: mọi read đều thấy write mới nhất đã hoàn tất.
- **Availability (A)** — Mọi request tới node còn sống đều nhận response (không lỗi, không timeout).
- **Partition Tolerance (P)** — Hệ vẫn tiếp tục hoạt động khi message giữa các node bị mất.

**Hệ quả:** Vì partition trong hệ phân tán là **không thể tránh khỏi** (cáp đứt, switch lỗi, container bị
cắt mạng), hệ thực tế luôn phải chọn **P**, và khi partition xảy ra chỉ được chọn **C** hoặc **A**.

## 2. PACELC — mô hình mở rộng

Khi **P**artition: chọn **A** hay **C**.
Khi **E**lse (không partition): chọn **L**atency hay **C**onsistency.

PACELC hữu ích cho MongoDB vì MongoDB **không cố định** CP hay AP — hành vi phụ thuộc
**read preference / read concern / write concern**, tức là có thể điều chỉnh điểm rơi trên
phổ Consistency ↔ Latency.

## 3. MongoDB Replica Set — cơ chế

- **Primary** nhận mọi write, ghi vào **oplog**.
- **Secondary** replicate oplog liên tục.
- **Election** diễn ra khi primary mất → cần **majority** (2/3) đồng ý mới bầu primary mới.
- Nếu mất majority → **không write được** (hành vi CP-like).
- Nếu client đọc từ secondary còn sống với `secondaryPreferred` → vẫn đọc được nhưng
  có thể **stale** (hành vi AP-like).

### 3.1. Tham số điều khiển

| Tham số | Giá trị | Ý nghĩa |
|---|---|---|
| `writeConcern.w` | 1 / majority | Số node phải ack trước khi trả OK |
| `writeConcern.j` | true / false | Ghi vào journal trước khi ack |
| `readConcern` | local / majority / linearizable | Mức "nhìn thấy" dữ liệu khi đọc |
| `readPreference` | primary / primaryPreferred / secondary / secondaryPreferred / nearest | Node nào phục vụ read |

### 3.2. Ma trận hành vi dự kiến cho 4 kịch bản

| Kịch bản | Read pref | Write concern | Hành vi dự kiến |
|---|---|---|---|
| **EXP01** — 3 node bình thường | primary | w=1, j=true | 100% success, latency thấp |
| **EXP02** — cô lập secondary (mongo3) | primary | w=majority | Write vẫn OK (mongo1+mongo2), read OK. Nếu đọc từ mongo3 → fail và fallback |
| **EXP03** — cô lập primary (mongo1) | primary | w=majority | Write fail sau timeout, election 10–20s, read từ secondary vẫn OK (stale) |
| **EXP03'** — cùng EXP03 | secondaryPreferred | — | Read vẫn OK (AP-like) nhưng có thể stale |
| **EXP04** — phục hồi | primary | w=majority | Convergence, replication catch-up, dữ liệu 3 node khớp lại |

## 4. Kết luận

- **Không** khẳng định "MongoDB là CP" hoặc "AP".
- MongoDB là hệ **điều chỉnh được (tunable)** — hành vi được quyết định bởi cấu hình.
- Thực nghiệm EXP01–EXP04 phải **đo** hành vi này thay vì suy đoán.
